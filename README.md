# BitflowOS

**Verifiable AI Bitcoin yield, on Starknet.**

BitflowOS is the first BTCFi vault where the AI agent's decisions are hardware-attested before any capital moves. Users deposit BTC wrapper assets, and a policy-bound Kimi agent prepares risk-aware yield allocations across Vesu, Endur, and Ekubo. Every recommendation is verified through a 0G Sealed Inference TEE before it reaches the chain — no blind trust, no black box.

> **Live on Starknet Sepolia** · [bitflow-os.vercel.app](https://bitflow-os.vercel.app)

---

## How It Works

```
Deposit BTC wrapper
  → Kimi generates yield allocation
  → 0G TEE attestation verifies the recommendation
  → You confirm
  → Backend submits attestation + router rebalance in one tx
  → Farcaster alert delivered
```

Rebalancing is **human-confirmed**. The agent prepares, attests, and explains — you approve. Capital never moves without your explicit confirmation.

## Status

Current network target: **Starknet Sepolia**.

The current system is suitable for demo, integration, and capped test deployments. It is not yet approved for uncapped mainnet user funds.

Current execution model:

- Deposits are user-signed Starknet transactions.
- AI recommendation is generated by Kimi, with conservative fallback logic available.
- 0G provider verification (TEE attestation) is checked before a recommendation is considered verified.
- Capital deployment is **human-confirmed** in the app.
- On confirmation, the backend executor submits one Starknet transaction containing:
  - attestation registry submission
  - strategy router `rebalance`
- Rebalancing is not currently automatic on a timer.
- Farcaster alerts require the user to add/enable the Mini App so Farcaster provides notification token details.

## Core Features

### BTC Yield Vault

BitflowOS provides a Starknet vault for supported BTC assets. Users deposit a supported BTC wrapper and receive vault shares. The vault tracks:

- supported assets
- user shares
- per-asset user shares
- total assets
- idle liquidity
- router-managed strategy balances

### Starkzap Transaction Execution

The frontend routes Starknet transactions through Starkzap. Deposit execution uses one multicall:

1. token `approve`
2. vault `deposit`

The app uses Starkzap-compatible account access for:

- external Starknet wallet
- Privy-backed embedded wallet path
- Cartridge passkey/session wallet path

### Agent Terminal

The Agent Terminal is the product's guided allocation surface. It:

- welcomes the user
- checks wallet/login state
- reads live vault state
- detects deposits
- requests a Kimi allocation
- checks policy/0G verification (TEE Attestation)
- asks for explicit confirmation
- triggers backend capital deployment
- checks Farcaster notification readiness
- supports user commands such as claim/withdraw

The agent persists pending confirmation state per wallet in browser storage so refreshing the page does not immediately restart the allocation sequence.

If a connected Starknet wallet has no test BTC wrapper balance, the agent can mint a demo `SBTC_TEST` token through the built-in faucet so the user can test the deposit and allocation flow.

### Kimi AI Allocation

When `KIMI_API_KEY` is set, the backend calls Kimi through Moonshot-compatible chat completions. The model returns strict JSON containing:

- strategy weights
- confidence score
- risk checks
- reasoning

The backend normalizes the response, enforces policy limits, adds idle reserve when needed, and blocks unsafe recommendations.

### 0G Verification

The backend verifies the configured 0G Compute provider before marking recommendations as 0G verified. It supports:

- provider verification through `@0glabs/0g-serving-broker`
- local report storage under `ZG_REPORTS_DIR`
- response verification when a 0G response id/chat id is available

### Router Rebalance

After the user types `confirm`, the backend executor submits an on-chain transaction that:

- submits an attestation hash to `AttestationRegistry`
- calls `StrategyRouter.rebalance`
- moves vault idle funds into enabled strategies based on approved target BPS weights

One transaction hash can contain multiple allocation legs because the executor uses a Starknet multicall.

### Native BTC Bridge

BitflowOS includes Atomiq integration for native BTC and Lightning BTC onboarding to Starknet.

The bridge path is:

```
BTC or Lightning BTC
  → Atomiq quote
  → user sends BTC to quoted address
  → Atomiq claims/wraps to Starknet output token
  → user deposits received wrapper into BitflowOS vault
```

### Farcaster Mini App Alerts

BitflowOS ships a Farcaster Mini App manifest and alert flow. Users can:

- save a Farcaster username to a Starknet wallet
- open BitflowOS inside Farcaster
- type `enable` in the Agent Terminal when prompted
- grant notification permission
- receive alerts for enabled event types

Alert preferences are user-configurable on the Alerts page.

## User Flow

### Wrapped BTC Deposit Flow

```
User connects wallet
  → app reads Starknet address
  → app reads vault state
  → user opens Deposit BTC
  → user selects supported wrapper
  → backend builds approve + deposit calls
  → Starkzap submits one multicall
  → vault mints yBTC/share position
  → agent detects indexed shares
  → agent requests Kimi allocation
  → 0G verification passes
  → user types confirm
  → backend executor submits attestation + rebalance
```

### Native BTC Flow

```
User connects Bitcoin wallet
  → app creates Atomiq quote
  → user sends BTC to quote address
  → Atomiq claims output token to Starknet address
  → user deposits output token into BitflowOS vault
```

### Rebalance Flow

```
Vault has deposit
  → Kimi recommendation generated
  → deterministic policy checks pass
  → 0G provider verification passes
  → user confirms
  → backend executor submits on-chain transaction
  → router rebalances enabled strategy routes
```

Current rebalance execution is **not automatic**. The backend has the execution machinery, but scheduled monitoring and Farcaster-confirmed rebalance prompts are future work.

### Withdraw Flow

```
User has yBTC/share position
  → user clicks Withdraw
  → backend builds vault withdraw call
  → Starkzap submits wallet transaction
  → frontend dispatches vault refresh
  → backend sends Farcaster withdrawal alert if notifications are enabled
```

## Native BTC Bridge Via Atomiq

Supported input sources:

- `BTC`
- `BTCLN`

The backend uses:

- `@atomiqlabs/sdk`
- `@atomiqlabs/chain-starknet`
- `@atomiqlabs/storage-sqlite`

Bridge records are tracked as `BridgeIntentRecord` with statuses:

- `quote_created`
- `payment_detected`
- `btc_confirmed`
- `claimed_to_starknet`
- `expired`
- `failed`

Security properties:

- Backend never sees Bitcoin private keys.
- User sends BTC directly to the Atomiq quote address.
- Atomiq output is sent to the user's Starknet wallet.
- Vault deposit still requires explicit user-signed Starknet transaction.

### Contract Responsibilities

#### YieldVault

- accepts supported asset deposits
- mints vault shares
- tracks global and per-asset positions
- tracks idle liquidity
- restricts strategy movement to router
- supports withdrawals

#### StrategyRouter

- validates attestations
- enforces strategy caps
- moves vault capital into adapters
- records strategy positions
- unwinds strategy positions when target BPS decreases

#### AttestationRegistry

- stores submitted attestation hashes
- restricts submitter
- supports submitter rotation
- exposes attestation consumption for router validation

#### Adapters

- `Erc4626VaultAdapter`: routes assets into ERC4626-compatible vaults.
- `EkuboAdapter`: routes assets into configured Ekubo LP positions with explicit slippage controls.
- `LeveragedVaultAdapter`: test/demo leveraged route with health-factor checks.

## Security Posture

### Non-Custodial User Funds

Users sign their own deposits and withdrawals. The backend does not receive user wallet private keys.

### Backend Executor

The backend executor key can submit router deployment/rebalance calls after user confirmation. This key is sensitive and must be stored only in backend secrets. It must be authorized on-chain as the required submitter/executor.

### Farcaster Tokens

Farcaster notification tokens are sensitive app-user notification credentials. They are stored in Postgres and must not be exposed to the frontend after capture.

### 0G Key

`ZG_PRIVATE_KEY` is an EVM key used for 0G broker/provider verification. Store only in backend secrets.

### Native BTC

The backend never asks for a Bitcoin private key. Bitcoin payment is made by the user's Bitcoin wallet to an Atomiq quote address.

### Mainnet Readiness

The system should not be used for uncapped mainnet deposits until:

- all security review blockers are addressed
- protocol-specific live integrations are verified
- strategy caps and asset caps are finalized
- emergency controls are tested
- monitoring and incident runbooks are complete
- native BTC bridge quote and claim paths are proven for production assets
